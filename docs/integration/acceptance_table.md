# Integration acceptance table

Format: **requirement → implementation entry point → verification evidence
→ status**. Status uses five categories, not a binary done/unfinished:

- **阻塞 (blocks current experiments)** — must be resolved before a normal
  experiment can run correctly.
- **需要 (capability needed now)** — not blocking, but something the lab
  actually uses today.
- **可选 (optional enhancement)** — a real capability with no demonstrated
  current need; welcome if someone asks for it, not pursued speculatively.
- **不做 (explicitly not doing)** — considered and declined, with the
  reason recorded so it isn't silently revisited.
- **待实机 (needs future real-hardware verification)** — simulated-only
  today; nothing here claims physical correctness.

Not tested against every theoretical combination, and not a full parity
copy of junjiebranch's historical planning documents — neither of those is
treated as a defect by itself (see `decision_log.md`'s 2026-10-15 entries
for why).

  not just these rows — see the final summary for what real-hardware
  verification would actually need to cover.

  are recorded so a real future request doesn't have to re-discover the
  same analysis, not as a backlog to work through.

## Current acceptance (baseline `aa5f3d1`)

**Baseline.** `codex/integration` = `aa5f3d14ce4940fbe24c6ef133f8f3b91610a270`, clean tree.
`origin/ola-branch` = `5014fc8f` (the integration's branch point; 40 commits ahead, 39 files,
22 under `src/`); local `ola-branch` = `f3817964`; `junjiebranch` = `2528c1c4` (also `origin/junjiebranch`),
which is an ancestor of the integration branch — the comparison with junjie is therefore about
which behaviour was carried into ola's structure, not about a diff. Neither original branch was
modified. The 249-test offline suite passes at this baseline.

**How to read the entries.** Each row follows the chain *preparation → parameter source → order →
wait/parallel → completion judged by → output → state after stop or failure*. Four distinctions
are used throughout and must not be collapsed:
- *requested* (UI/definition) → *sent* (what the driver actually transmitted, e.g. the clamped Z
  target or AD2's achieved frame rate) → *read back* (the device's answer);
- *command accepted* is not *action finished* unless the step waits for a read-back;
- *complete acquisition kept* (atomic folder, `acquisition_status: "complete"`) is not
  *partial frames kept* (an incomplete acquisition is discarded, deliberately, `f717884`);
- *controller reports stable* (read-back temperature within tolerance for the settle time, then a
  fixed hold) is not *sample at thermal equilibrium* (nothing measures that).

### Accepted differences (and why)
- Incomplete acquisitions are discarded, not kept as partial frames: a half-written experiment would look usable; completed experiments stay and are marked.
- TIFF + JSON instead of TDMS: no document shows an external consumer that needs TDMS (junjie's `HANDOVER.md` only lists "validate TIFF … against downstream analysis" as a to-do, with no tool named).
- No audit/protection/configuration subsystem from junjie: the read-back checks and error reasons that matter are present as named in the table; adding more was not requested.
- The flush/save overlap exists in both branches; the integration's explicit failure containment differs and was kept.

### Blocking items for current use
None in code that I could find with the checks above. Before relying on **real** data (not code defects, physical checks only you can do): measure the DIO0→camera trigger edges and frame spacing once (`HW-TIMING-001`), confirm the laser path (`HW-LASER-PATH-001`), and decide the TEC-after-run policy.

Z-stack failure reason / run identity in `metadata.json`; `stage_move` position confirmation; TEC applied values in `experiment.json`; Recover-fault button; elapsed/remaining time; ROI statistics, profiles, frame review in the viewer; a preset/recipe manager.
